Reliability & limits

AccessScan runs on a free hosted instance, so it has real limits: cold starts, one scan at a time, and history that lives only in memory. This page explains exactly what happens, including when things go wrong.

Cold starts

If the server has been idle for a while, the first request can take roughly 50 seconds while the free-tier host wakes up. You do not need to do anything special: submit your scan, watch the progress bar, and wait. The progress indicator is designed to show this wait rather than leave you guessing. Once the server is warm, scans start quickly again.

One scan at a time

AccessScan runs a single scan at a time. If someone else is already scanning, your request is refused politely: the page shows a friendly “a scan is already running” message with the server’s suggested wait time (Retry-After), and you can simply try again a minute later. There is no queue, if you need several scans, run them one after another.

Scan deadline

Every scan has a deadline of about 3 minutes. A single scan fetches the target page, renders it, and runs the accessibility engine, on a slow or heavy site that can take a while, and the deadline keeps a runaway scan from holding the single slot forever. If the deadline is hit mid-scan, you still get the results collected so far.

Partial results are normal

A single failing page does not kill the whole scan. If one page cannot be reached or times out, that page is marked with an error and the scan continues with the rest. When the overall time limit cuts a crawl short, the report says “Scan time limit reached” and marks which pages were not checked. Treat a partial report as “these pages were checked”; it is not a claim that the whole site is clean.

History is in-memory only

Scan history is stored in the server’s memory and capped at the 20 most recent scans. That means history disappears whenever the server restarts or redeploys, which, on a free host that sleeps when idle, can happen often. To keep a report, export it (HTML, JSON, or PDF) right after the scan. Your browser separately keeps its own recent-scan list in local storage, so “Recent scans” in the interface may show scans the server no longer has, viewing one may fail until the server history is repopulated.

Rate limits

To keep the free instance fair for everyone, requests are rate-limited: roughly 10 requests per IP per 10 minutes plus a global cap of about 60 requests overall. These limits are configurable via environment variables, so the exact numbers can change with deployments. Hitting a limit produces a clear message, not an error page.

What failures look like

  • Server waking up: a long wait with the progress bar, let it finish.
  • Scan already running: a friendly message with a suggested retry time.
  • Rate limited: a clear “too many requests” style message, not a raw error code.
  • Site unreachable or slow: the scan completes with per-page errors marked in the report.
  • Time limit reached: partial results, clearly labelled.
  • History gone: recent scans may not load after a restart or redeploy, export reports you want to keep.

AccessScan is designed to explain problems in plain language. You should never see a bare HTTP status code as your only feedback, if you do, that is a bug worth reporting.

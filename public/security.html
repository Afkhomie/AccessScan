Security

Security transparency

AccessScan is a tool that fetches and renders web pages — which makes it a potential vector for the very problems it scans for. This page states plainly what is protected, and what is not. No marketing, no claims we can't back.

What is protected

AccessScan fetches pages you point it at, which means it could in principle be tricked into reaching places it shouldn't — like your router's admin page or a cloud metadata endpoint. Several independent guards exist to stop that.

SSRF guard: internal addresses are rejected

Before a scan ever starts, every submitted URL is checked:

  • Protocol: only http:// and https:// are accepted.
  • Private and reserved IPs: loopback (127.x), RFC 1918 ranges (10.x, 172.16–31.x, 192.168.x), link-local and cloud-metadata addresses (169.254.x), CGNAT (100.64–127.x), multicast/reserved ranges, and IPv6 loopback, link-local, unique-local and mapped addresses are all refused.
  • Internal hostnames: localhost, .localhost, .local, .internal, .lan, .home, and known internal names like metadata.google.internal are refused.
  • DNS resolution: for domain names, the hostname is resolved and every returned address must be public — if any answer is private or internal, the scan is refused.

Redirect hops are validated before connecting

A public URL can redirect to an internal one. AccessScan installs a per-page interception layer (via the browser's debugging protocol) that re-runs the same address check on every request, including each redirect hop, before it connects. A redirect to a disallowed address fails the request and the scan reports it as blocked rather than silently following it. Pop-up windows get the same treatment, and resource types the scan doesn't need are blocked outright.

Credentials are stripped from stored results

If you scan a URL containing user:password@, the credentials are used for the fetch itself but are removed from the copy that is stored — scan history, reports, and exports never persist them.

Scan data is escaped everywhere it is rendered

Page content, rule descriptions, URLs, and error messages from scanned sites are untrusted input. All of it is HTML-escaped before it reaches the results page or an exported report, so a hostile page cannot inject markup or scripts into AccessScan's own interface.

Rate limiting

Scan creation is rate-limited to protect the shared instance: roughly 10 scans per IP per 10 minutes plus a global cap of 60 scans per window. Limits are configurable via environment variables. (See the reliability page for how these behave in practice.)

Production access gate

When deployed on a hosted platform, a shared-secret header (PROXY_SECRET) gates the backend: requests without the correct key are rejected before reaching the app, so only the front-end proxy can use the API.

Response headers and resource blocking

Every response carries X-Frame-Options: DENY (no clickjacking) and X-Content-Type-Options: nosniff (no MIME confusion). During a scan, resource types that aren't needed for the accessibility check — images, media, fonts, and similar — are blocked, which both speeds scans up and reduces the attack surface of whatever the scanned page tries to load.

What is not protected — known limits

Honesty matters more than a clean-looking page. These are real limitations, stated plainly.

DNS rebinding (time-of-check vs. time-of-use)

The SSRF guard resolves a hostname's DNS once, at submission time. The browser re-resolves DNS again when it actually navigates — seconds later. A malicious domain with very short DNS TTLs could in theory answer with a public IP for the check and a private IP for the navigation. This is a known shortcut, accepted because AccessScan is designed as a local, single-user tool where the person scanning controls the input. On the hosted instance the practical risk is limited by the PROXY_SECRET gate and rate limits, but the gap exists.

Scanned pages run real JavaScript

AccessScan renders pages in a real browser so it can measure what users actually experience — which means the scanned site's JavaScript executes in the scanner's browser. This is by design, and it means a hostile site could attempt browser-level attacks (exploits, fingerprinting). Mitigations: resource blocking, no stored credentials beyond what you type, results are escaped, and the scan process holds no user session or sensitive data. It is still a reason to treat scan results from untrusted sites with normal caution.

Single-user trust model

AccessScan assumes the person running a scan is the person who chose the URL. There are no per-user accounts or per-user isolation: scan history, rate-limit buckets (when keyed by IP), and exported reports are shared across everyone using the same instance. On a multi-user deployment this model is weaker than a fully isolated service.

Scan IDs are unguessable, not secret

Scan IDs are generated from 12 random bytes (scan_ + 24 hex characters), so they can't be enumerated. However, anyone holding a scan link can view that scan's results — the report endpoints are unauthenticated by design, because there is no account system. Treat a scan URL like a shared document: fine for your own use, don't post links to sensitive scans publicly.

Reporting a security issue

If you believe you've found a security vulnerability in AccessScan itself — not in a site you scanned — please open an issue at github.com/Afkhomie/AccessScan/issues describing it responsibly. AccessScan is operated by Afkhomie via GitHub.
